rem architecture

A local-first personal memory layer. Agents send it raw conversation; rem's own LLM extracts facts, a rule-based trust step labels them, and one daemon stores them Mem0-style: canonical memories in a Qdrant vector store, history and operational state in SQLite.

Canonical knowledge

Qdrant · local mode

~/.local/share/rem/qdrant/ · opened only by the daemon
  • rem_memories__bge-small_384 M1vector = embed(text). Payload is the memory: text, hash, scope, project_id, provenance, status, evidence_source, observed_at, source, session_id, job_id, entity_ids[], created_at, updated_at
  • + BM25 sparse vector M6keyword search in the same collection, the same way Mem0 does it
  • rem_entities__… M7name, type, aliases[], scope, memory_ids[]
  • rem_relations__… M8source → type → target, evidence memory_ids[], provenance, status

Swap the backend through the VectorStore interface. To move to a Qdrant server, change path to url in config.

Operational state + audit, not the fact ledger

rem.db · SQLite

~/.local/share/rem/rem.db · WAL mode
  • historytarget_kind (memory · entity · relation), event (ADD · UPDATE · DELETE · CONFIRM · CORROBORATE · MERGE · REEMBED), old → new, actor, job_id
  • messagesredacted raw turns, used as extraction context
  • sessions · projects(source, session_id) · git root and remote
  • jobsthe durable ingestion queue, with leases
  • metaschema version, active embedder and collection names

Changing the embedding model creates new collections; rem reembed copies payloads with the same ids, and the old collections are kept until finalize.
